# Function-level evaluation

This page reports how the committed per-function model (`model/functions.json`) performs on builds it was not fitted on, how that hold-out was chosen, and what the numbers do and do not cover. It is generated by `training/train_functions.py` at the same time as the model, so the numbers and the file ship together.

## The dataset

Per-function features extracted by `compid functions-batch --features` from **1297 builds with extractable functions** (342507 functions): ELF rows via the symbol table (or the stripped-x86-64 prologue heuristic), Mach-O rows via `LC_SYMTAB`, and PE rows via the export directory. Every function inherits its build's manifest labels; nobody labels functions by hand.

| axis | builds (functions) |
|------|--------------------|
| compiler_family | clang (315425 fns), gcc (27082 fns) |
| opt_level | O0 (512), O1 (65), O2 (532), O3 (65), Os (74), Oz (49) |
| arch | aarch64 (200), arm (102), riscv64 (204), x86_64 (791) |
| os | linux (267626 fns), macos (74873 fns), windows (8 fns) |

## The hold-out is split by build, not by function

The 342507 functions are not independent rows: the functions of one binary share padding, literal pools, and every per-build idiosyncrasy, so a per-function random split would leak a build into its own hold-out. The split shuffles whole build_ids (20% of builds held out, seed 42, stratified by the build's compiler_family) and every metric below is computed over the held-out builds' functions. All functions of a build sit on exactly one side of the split.

The *build majority* column pools each held-out build's per-function votes and scores the winning class against the build's label - the operation `scripts/mixed_demo.sh` performs on a binary assembled from two toolchains. Per-function top-1 is the harder, unaggregated number.

## Reading the weak spots honestly

`opt_level` lags badly on macro-F1 relative to top-1, which is the signature of class imbalance plus sibling-class confusion: optimization levels shade into one another (O2 and O3 emit the same shapes for most functions), and small classes have almost no functions to learn from at function granularity.

There is also structural label noise the whole-binary trainer never faces. Every function inherits its build's labels, so the thousands of libc functions inside a statically linked binary are labeled with the container's optimization level even though libc itself was compiled once, at its own flags, by whatever built the sysroot. Those functions dominate the function count of static builds and drag the per-function metrics for `opt_level` in particular; the per-function `compiler_family` numbers survive the same noise because the sysroot is still built by a member of the same family in this seed (zig compiles its bundled musl with clang).

## How the model is trained

One multinomial logistic regression per field (`LogisticRegression(max_iter=3000, C=4.0, class_weight='balanced')`) over L2-normalized integer counts - the whole-binary recipe plus class weighting, because function rows inherit the matrix's toolchain skew (clang rows outnumber gcc roughly 2.5:1) and an unweighted fit let the prior swallow minority-toolchain functions inside mixed binaries. Disable with `--no-balanced`. Features seen in fewer than 50 functions are dropped (the whole-binary trainer's floor is 150; functions are small, so rare n-grams survive less often). The export is `compid-model/v1` - the same format as `model/model.json` - with only `compiler_family` and `opt_level` fields.

## Stripped-binary boundaries — measured, not promised

`compid functions` no longer refuses a stripped binary outright. For x86-64 ELF with no symbol table, two conservative scans over the executable sections propose function starts, and their union is merged by the same decode-aware overlap logic; extraction proceeds with synthesized `func_<hex addr>` names, marked `source: heuristic` in the JSON and by a header note in the table. The same scans extend to the other containers as of this round: a PE without an export table is scanned over its executable raw-data sections (candidates report as RVAs, bytes read through `PointerToRawData`), and a Mach-O without a symbol table over `__TEXT,__text` and `__TEXT,__stub_helper` (virtual addresses matching `LC_SYMTAB`'s convention; other sections are excluded on purpose, since Mach-O has no per-section execute flag and a scan over `__unwind_info`/`__eh_frame` would misread structured data). Synthetic stripped PE32+/Mach-O fixtures pin the address conventions in `tests/stripped_pe_macho_test.rs`. Honest scope note: the numbers below are ELF-only - no stripped PE/Mach-O ground truth ships, so those paths carry the machinery and its tests, not a published precision/recall.

The first scan is the prologue-pattern set (one const array in `src/functions.rs`): `push rbp; mov rbp, rsp` and `push rbx; mov rbx, rdi` at 16-byte alignment, `endbr64` at any alignment with a frame-setup followup — and, at aligned sites, none — plus the paired-`lea` crt-stub shape and PLT-stub exclusions. The second scan is direct call-target analysis, which catches functions that lack a frame-setup prologue (cold clones, shrink-wrapped `-Os` entries): with the same length-aware x86-64 decoder the clean-window count uses, each executable section is disassembled linearly (skipping undecodable bytes one at a time), and every decoded direct `call rel32` (opcode `E8`) records the target `instruction address + instruction length + signed displacement` as a candidate start. A call target qualifies when it falls inside the scanned section (cross-section branches, e.g. into `.plt`, are thereby excluded, matching the prologue scan's PLT treatment), decodes cleanly for at least 16 bytes from the target, does not open with a PLT-stub shape (`endbr64; jmp *GOT`, bare `jmp *GOT` / `push *GOT`, or `push imm32; jmp rel32`), and is not already a prologue candidate. Direct `jmp rel32` (`E9`) targets were measured too and stay out: they add tail-thunk entries but far more loop back-edges and goto joins, which split otherwise-correct functions — with `E9` included the same sweep lands at precision 0.4334 / recall 0.9215 (F1 0.5896). The choice is pinned in one const (`CALL_TARGETS_INCLUDE_JMP`) in `src/functions.rs`, and the whole candidate union runs through the same merge pipeline, so a start found only by a call target is indistinguishable from a prologue start.

The heuristic is measured, not asserted. `compid functions <bin> --measure` runs the scan on an unstripped binary and scores its starts against the symbol table's starts at a ±8-byte tolerance; `scripts/measure_boundaries.py` sweeps a stratified sample over the manifest. The numbers below are the sweep over 40 linux-gnu x86_64 manifest rows (8 per optimization level, O0 through Os, seed 42), before and after the call-target scan joined the prologue scan — re-run `scripts/measure_boundaries.py` against any manifest to reproduce the shape of this table:

| pooled over 40 binaries | prologue scan only | prologue + call targets |
|-------------------------|--------------------|-------------------------|
| symbol-table starts (ground truth) | 2713 | 2713 |
| heuristic starts | 2376 | 2535 |
| matched within ±8 bytes | 2330 | 2489 |
| precision | 0.9806 | 0.9819 |
| recall | 0.8588 | 0.9174 |
| F1 | 0.9157 | 0.9486 |

The call-target scan buys 159 recovered ground-truth starts while adding only 13 unmatched starts — precision ticks up, not down, because a direct `call` is strong evidence of a real entry point. Per optimization level, pooled precision stays at 0.96-1.00 everywhere and pooled recall is 0.75-0.95 (O0 0.92, O1 0.76, O2 0.95, O3 0.75, Os 0.75). Eight further rows were skipped because their symbol tables carry no function symbols at all (zig-cc builds that list only undefined imports) — no ground truth, no measurement.

What the residual misses are, honestly:

- Functions smaller than the 16-byte minimum: `.fini` (13 bytes) on every dynamic binary, and any function abutting its section's end.
- Functions never reached by a direct `call` and matching no prologue pattern: entries reached only through indirect dispatch (function pointers, vtables) and never-called leftovers.
- These cost recall, not precision: across the sweep, wrong starts are rare (pooled precision 0.98), and the ones that occur sit at legitimate-looking prologues or called addresses in padding.

Recall is bounded, and that is the point of the conservative set: a missed function costs one vote in the per-binary majority, while a false start injects a vote for whatever the padding decodes as. The stripped mixed-toolchain demo (`scripts/mixed_demo.sh`, second half) runs the same gcc/zig majority assertion on a `strip`ped copy and passes: the gcc half majority-predicts gcc and the zig half majority-predicts clang (5 of its 6 attributed functions, with 16 heuristic functions on the stripped copy against 11 before the call-target scan).

## Limitations

- Function boundaries come from the container's symbol sources: the ELF symbol table (plus the stripped-x86-64 prologue heuristic), the PE export directory, and the Mach-O `LC_SYMTAB`. What yields no function rows: a PE without an export table (most plain Windows executables), a Mach-O without a symbol table, and a stripped non-x86-64 ELF. The PE rows are export-table functions only - the bulk of a DLL's internal (non-exported) functions is invisible to this path, and the last export of a section carries a section-end-derived size rather than a true one.
- Every function of a build shares the build's labels. A function inlined from a vendored, differently-built library is labeled with its container's toolchain, not its true generator; the mixed-demo split is the sanity check that the model reads code shape, not container residue (functions carry no `sec:`, `ent:`, or `cmt:` features).
- Same-toolchain-version bias as the whole-binary seed: a toolchain the matrix never saw will get confident wrong answers.
- Small functions (under a few dozen bytes) carry little signal; their votes are near-noise, which is one reason the majority vote matters more than any single function's confidence.
