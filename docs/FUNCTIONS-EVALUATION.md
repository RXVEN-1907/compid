# Function-level evaluation

This page reports how the committed per-function model (`model/functions.json`) performs on builds it was not fitted on, how that hold-out was chosen, and what the numbers do and do not cover. It is generated by `training/train_functions.py` at the same time as the model, so the numbers and the file ship together.

## The dataset

Per-function features extracted by `compid functions-batch --features` from **1008 unstripped ELF builds** (266791 functions). Every function inherits its build's manifest labels; nobody labels functions by hand.

| axis | builds (functions) |
|------|--------------------|
| compiler_family | clang (239835 fns), gcc (26956 fns) |
| opt_level | O0 (394), O1 (65), O2 (410), O3 (65), Os (74) |
| arch | aarch64 (98), arm (102), riscv64 (204), x86_64 (604) |

## The hold-out is split by build, not by function

The 266791 functions are not independent rows: the functions of one binary share padding, literal pools, and every per-build idiosyncrasy, so a per-function random split would leak a build into its own hold-out. The split shuffles whole build_ids (20% of builds held out, seed 42, stratified by the build's compiler_family) and every metric below is computed over the held-out builds' functions. All functions of a build sit on exactly one side of the split.

## Results (hold-out builds, per function)

| field | classes | functions | top-1 | top-3 | macro-F1 | build majority top-1 |
|-------|---------|-----------|-------|-------|----------|----------------------|
| `compiler_family` | 2 | 61190 | 0.9970 | 1.0000 | 0.9944 | 0.9950 |
| `opt_level` | 5 | 61190 | 0.8836 | 0.9997 | 0.6322 | 0.8317 |

The *build majority* column pools each held-out build's per-function votes and scores the winning class against the build's label - the operation `scripts/mixed_demo.sh` performs on a binary assembled from two toolchains. Per-function top-1 is the harder, unaggregated number.

## Reading the weak spots honestly

`opt_level` lags badly on macro-F1 relative to top-1, which is the signature of class imbalance plus sibling-class confusion: optimization levels shade into one another (O2 and O3 emit the same shapes for most functions), and small classes have almost no functions to learn from at function granularity.

There is also structural label noise the whole-binary trainer never faces. Every function inherits its build's labels, so the thousands of libc functions inside a statically linked binary are labeled with the container's optimization level even though libc itself was compiled once, at its own flags, by whatever built the sysroot. Those functions dominate the function count of static builds and drag the per-function metrics for `opt_level` in particular; the per-function `compiler_family` numbers survive the same noise because the sysroot is still built by a member of the same family in this seed (zig compiles its bundled musl with clang).

## How the model is trained

One multinomial logistic regression per field (`LogisticRegression(max_iter=3000, C=4.0, class_weight='balanced')`) over L2-normalized integer counts - the whole-binary recipe plus class weighting, because function rows inherit the matrix's toolchain skew (clang rows outnumber gcc roughly 2.5:1) and an unweighted fit let the prior swallow minority-toolchain functions inside mixed binaries. Disable with `--no-balanced`. Features seen in fewer than 50 functions are dropped (the whole-binary trainer's floor is 150; functions are small, so rare n-grams survive less often). The export is `compid-model/v1` - the same format as `model/model.json` - with only `compiler_family` and `opt_level` fields.

## Limitations

- Function boundaries come from ELF symbol tables only: the training set is unstripped ELF, and that is also the only input `compid functions` accepts today. Stripped-binary heuristics and PE/Mach-O symbol sources are future work.
- Every function of a build shares the build's labels. A function inlined from a vendored, differently-built library is labeled with its container's toolchain, not its true generator; the mixed-demo split is the sanity check that the model reads code shape, not container residue (functions carry no `sec:`, `ent:`, or `cmt:` features).
- Same-toolchain-version bias as the whole-binary seed: a toolchain the matrix never saw will get confident wrong answers.
- Small functions (under a few dozen bytes) carry little signal; their votes are near-noise, which is one reason the majority vote matters more than any single function's confidence.
